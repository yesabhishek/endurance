# Security

## Reporting a vulnerability

Please open a private security advisory on GitHub (Security → Advisories → New draft) instead of a public issue. Include steps to reproduce and the version or commit you tested.

## Secrets this project handles

| Secret | Where it lives | Protection |
| --- | --- | --- |
| `APP_SECRET` | `.env` on the host | Never committed; generated by `scripts/setup.sh` |
| Postgres and Redis passwords | `.env` on the host | Services are not published outside the compose network |
| User passwords | Postgres | scrypt hash with per-user salt |
| Session tokens | Browser cookie (HttpOnly, SameSite=Lax) | Only a SHA-256 of the token is stored |
| Kite API secret, Kite access token, AI keys, Gmail tokens | Postgres | AES-256-GCM, key derived from `APP_SECRET`, bound to the owning user and purpose |

## Rotating APP_SECRET

1. Move the current value to `APP_SECRET_PREVIOUS` in `.env`.
2. Set a new `APP_SECRET` (`openssl rand -hex 32`).
3. Restart: `docker compose up -d`. Stored keys still decrypt with the previous secret and are re-encrypted with the new one the next time they're used.
4. Remove `APP_SECRET_PREVIOUS` once every user has used the app. Values that weren't re-encrypted by then need to be entered again.

Rotating does not sign anyone out, because sessions are random tokens rather than values signed with `APP_SECRET`. To force everyone to sign in again, delete the rows in the `Session` table.

## If a Kite API secret leaks

Regenerate it in the [Kite developer console](https://developers.kite.trade/apps), then paste the new secret in Settings → Zerodha Kite → Replace app keys. Removing the leaked value from git history does not undo the exposure; rotation does.

## Scope

Endurance is read-only towards Zerodha: the Kite client in `web/src/lib/kite/client.ts` implements only profile, holdings, mutual fund holdings, positions and session endpoints. Changes that add order placement are out of scope for this project.
